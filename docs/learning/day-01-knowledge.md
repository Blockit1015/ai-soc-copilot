## 知识点 2｜API、HTTP 与响应契约

**用自己的话解释：**
API是系统对外的窗口，HTTP是沟通规则。响应契约就是双方约定好请求哪个地址、返回什么状态码、JSON里有哪些字段。

**为什么今天必须学：**
让我明白了团队协作依赖稳定的契约。调用方不需要知道内部实现，只需要知道如何调用和判断成功与否。

**`GET /health` 的固定契约：**
HTTP状态码200，JSON响应体：{"status": "ok", "service": "ai-soc-copilot", "version": "0.1.0", "environment": "local-training"}

**一个常见误区：**
只要接口不报错就算成功，忽略响应体内容是否符合约定。

**我今天留下的证明：**
tests/test_health.py文件，不仅断言了状态码200，还断言了完整的JSON响应体。

**自测：只断言 HTTP 200 为什么不够：**
因为200只表示请求被成功处理，但响应体里的数据可能已经变了，这会导致依赖这个接口的调用方出错。

## 知识点 4｜健康检查、可观测性与事实边界

**用自己的话解释：**
健康检查是系统告诉外部这个服务入口现在是活的的接口

**健康接口今天能证明什么：**

**健康接口今天不能证明什么：**
不能证明告警、Agent、RAG、模型、数据库等功能可用，因为今天根本没做这些。

**一个常见误区：**
/health 返回200就等于项目完成

**我今天留下的证明：**

## 3 分钟工程说明提纲
1. 为什么从健康接口开始
在工程实践中，选择从健康接口作为起点，是因为它构成了一个最小可运行、可测试的入口。这个接口不依赖复杂的业务逻辑或外部数据库，能够以最纯粹的方式验证整个技术栈的连通性。它的目的是为了在最短时间内确保我们的开发环境、代码结构和自动化流程能够跑通，为后续构建复杂功能打基础。
2. 项目的工程结构
AGENTS.md：给AI的“说明书”，明确项目的代码规范、常用命令和禁止事项，确保AI生成的代码符合项目标准。
README.md：面向人类开发者的项目介绍，包含环境搭建步骤、运行方式和项目背景。
requirements.txt：锁定项目的Python依赖包及其版本，保证环境的一致性。
app/main.py：应用程序的入口文件，定义了FastAPI实例和核心路由。
tests/test_health.py：针对健康接口的自动化测试文件，用于持续验证功能的正确性。
3. 请求怎样流动
一个健康检查请求的完整生命周期清晰而简洁：当测试脚本或客户端发起一个GET /health请求时，FastAPI框架会首先捕获该请求，并根据路由规则将其分发给对应的Python处理函数。该函数执行后，会返回一个固定的JSON响应。最后，自动化测试框架pytest会捕获这个响应，并通过断言来验证其状态码和内容是否符合预期，完成一次验证。
4. 怎样使用 Codex
遵循了一个结构化的工作流：
Explain：让AI解释现有代码或需求，确保双方理解一致。
Plan：对于任何超过两三步的任务，先让AI列出实施计划和潜在风险，待确认后再执行。
Build：在计划确认后，让AI生成代码。
Debug：遇到报错时，提供完整的错误信息和上下文，让AI分析并修复。
Review：最后，让AI审查自己生成的代码，检查潜在问题。
5. 怎样证明
工程的价值在于可验证。我们的证明过程如下：
预期失败：在功能实现前，先运行测试，确认test_health.py会因为找不到接口而失败，这证明了测试本身是有效的。
最终测试：在代码编写完成后，再次运行pytest，确认所有测试通过，这是功能正确的直接证据。
接口访问：启动服务后，通过浏览器或curl命令直接访问/health端点，亲眼看到正确的JSON返回。
Git 证据：https://github.com/Blockit1015/ai-soc-copilot/commit/31a3855。
