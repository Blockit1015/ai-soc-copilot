## K03｜HTTP 状态语义

**我用自己的话解释：**
HTTP状态码是系统与外部沟通的代码：2xx表示成功，4xx表示调用方犯错，5xx表示自己崩溃了，使用状态码能让调用方知道下一步该怎么做

**`201 / 200 / 409 / 422` 各表示什么：**
201：首次成功创建了新资源
200：请求成功，且是安全的重放
409：请求意图相同，但内容变了，发生冲突
422：请求格式错误，拒绝

**为什么不能全部返回 `200`：**
如果都返回200，调用方就无法区分具体是什么问题，是真的创建成功了，还是网络卡顿重试了，还是数据冲突了，还是传错参数了，这会导致上游系统逻辑混乱

**它在今天哪个文件或测试里出现：**
app/api/investigations.py

**一个常见误区：**
把参数错误返回400而不是422

**今天的实际证据：**
测试文件中分别断言了这四种状态码

**离企业生产能力还差什么：**
还没有在响应体中统一返回自定义的错误码，目前只依赖HTTP状态码

## K04｜幂等键与载荷指纹

**我用自己的话解释：**
幂等键是调用方给这次请求贴的唯一单号。载荷指纹是对内容的哈希摘要，两者结合，既能防止网络卡顿导致的重复创建，又能防止有人用同一个单号偷偷内容

**为什么只保存幂等键还不够：**
如果只存键，当调用方用同一个键发了一个完全不同的告警时，我们会误以为是重放，从而返回错误的旧结果，或者更糟，直接覆盖掉旧结果

**键、指纹、首次响应三者的关系：**
键是字典的Key，指纹是Value的一部分，首次响应是Value的另一部分，收到请求时，先看键在不在，如果在，再比对指纹

**同键同载荷怎样处理：**
指纹一致，直接返回200和缓存的首次响应

**同键不同载荷怎样处理：**
指纹不一致，返回409Conflict，拒绝处理

**为什么冲突不能覆盖原结果：**
因为业务上这代表同一个请求意图被篡改了，覆盖会导致数据不一致，必须报错让调用方去检查代码

**它在今天哪个文件或测试里出现：**
app/services/idempotency.py

**一个常见误区：**
只要幂等键一样，就直接返回之前的结果，不看载荷有没有变

**今天的实际证据：**
test_reusing_key_with_different_alert_payload_is_rejected_without_replacing_record测试

**内存方案离生产幂等还差什么：**
内存字典重启就没了，且不支持多进程/分布式共享

## K05｜correlation_id

**我用自己的话解释：**
correlation_id是贯穿整个请求链路的追踪手环，不管这个请求经过了多少个微服务，只要带着这个手环，我们就能在海量日志中把它们串起来

**它与 `investigation_id`、`Idempotency-Key` 各自负责什么：**
Idempotency-Key：负责防重放
investigation_id：负责标识系统内部创建的业务实体
correlation_id：负责跨服务追踪

**为什么 D02 安全重放复用首次关联标识：**
因为重放本质上是同一个业务动作的延续，复用首次的 correlation_id，能让运维人员在排查时，把重试的请求和首次请求看作同一个事件

**生产系统为什么可能再增加独立 `request_id`：**
correlation_id可能是上游传过来的，如果上游没传或者传错了，就失去了追踪能力，系统内部自己生成一个request_id，能保证每次物理请求都有唯一标识

**它在今天哪个文件或测试里出现：**
app/api/investigations.py

**一个常见误区：**
把correlation_id和investigation_id混为一谈

**今天的实际证据：**
test_safe_replay_reuses_original_investigation_and_correlation_ids测试

**离跨服务追踪还差什么：**
还没有接入真实的分布式追踪系统，目前只是把ID透传并返回

### Q03

为什么首次请求、相同请求重放、冲突重放和非法输入不能都返回 `200`？

-因为调用方需要根据状态码决定下一步动作，全返回 200 会让调用方不知道具体出了什么错误

### Q04

为什么只保存 `Idempotency-Key` 不够，还要比较载荷指纹？内存方案有什么限制？

-只保存Key无法防止同键不同值的恶意篡改或调用方Bug
内存方案的限制是：重启丢失，且不支持多实例/分布式环境下的状态共享

### Q05

`correlation_id` 与 `investigation_id` 分别追踪什么？为什么安全重放要复用首次关联标识？

-investigation_id追踪业务实体（调查记录），correlation_id追踪请求链路。
重放复用是因为它们属于同一个业务意图，复用能让日志排查时把重试和首次请求关联起来

### Q06

为什么必须保存一次有效 RED、聚焦测试和完整回归？三者各自证明什么？

-RED证明测试有效；聚焦测试证明新的功能达标；完整回归证明没有破坏旧功能
